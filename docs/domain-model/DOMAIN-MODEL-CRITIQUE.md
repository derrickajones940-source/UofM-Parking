# AI Domain Model Critique

## Overview

I compared the first domain model generated by GitHub Copilot with my own domain model for the UofM Parking Survival App.

The AI draft was useful because it identified several concepts from the requirements, but I simplified the model to focus on the main entities needed by the current application.

## Where the AI Over-Modelled

The AI model included **ParkingRestriction** as a separate entity. My model instead treats parking restrictions as an attribute of a ParkingLot. The current application needs to display parking restrictions, but a separate entity is not necessary unless the application needs to manage different restrictions independently.

The AI also included **AlertSubscription**. This adds another entity to represent a user's choice to monitor a parking lot. I decided not to include it in my model because the current model can represent the notification requirement without adding a separate subscription entity.

The AI also included a conceptual **User** entity. The requirements mention users submitting reports and receiving notifications, but they do not require user accounts, authentication, or stored user information. I therefore did not make User a separate entity in my model.

## Where the AI Under-Modelled

The AI did not significantly under-model the core parking information. It included the main ParkingLot concept as well as reports and notifications.

However, my model separates the main concepts into three simple entities: ParkingLot, ParkingReport, and Notification. This makes the model easier to understand for the current version of the application.

## Unsupported or Assumed Relationships

The AI created relationships between **User and ParkingReport** and **User and ParkingLot through AlertSubscription**.

These relationships are based on the idea that users can submit reports and subscribe to parking lots. While the requirements mention users submitting reports and receiving alerts, they do not require a stored user account or a persistent user identity.

Because of this, I considered the User relationships to be assumptions rather than necessary domain relationships for the current model.

The AI also connected **AlertSubscription to Notification**. This relationship makes sense if the application stores individual subscriptions, but that level of modeling is not necessary for the current requirements.

## Where the AI Was Correct

The AI was correct to identify **ParkingLot** as the central entity.

It correctly included important parking information such as:

* total spaces
* available spaces
* parking status
* cost
* walking time
* parking restrictions
* availability update time

The AI was also correct to include **ParkingReport** because the requirements include reports about parking conditions.

The AI correctly included **Notification** because the requirements include notifications when a parking lot is filling up.

The AI also correctly recognized that parking status can potentially be derived from available spaces. This matches my decision not to create ParkingStatus as a separate entity.

## Why My Model Is Different

My model contains three main entities:

1. **ParkingLot**
2. **ParkingReport**
3. **Notification**

I chose these entities because they directly represent the main information the application needs.

I did not make **ParkingStatus** a separate entity because status can be calculated from the number of available spaces and total spaces.

I also did not create separate **User**, **AlertSubscription**, or **ParkingRestriction** entities because those concepts add additional structure that is not necessary for the current application model.

For example, restrictions can be stored as part of the ParkingLot information, while notifications can be associated directly with the ParkingLot.

## Overall Critique

The AI draft was useful as a first draft because it identified the major concepts in the application and considered several requirements that could affect the domain model.

However, I believe it models more detail than is necessary for the current version of the application. In particular, User, AlertSubscription, and ParkingRestriction introduce additional relationships and entities that are not required to implement the core parking functionality.

My model intentionally uses fewer entities. This makes the model simpler while still representing parking lots, parking reports, and notifications.

The main lesson from reviewing the AI draft is that an AI-generated domain model should be compared against the actual requirements instead of automatically accepting every entity and relationship it suggests.
